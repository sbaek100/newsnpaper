# PRD-05: 검색

| 항목 | 값 |
|---|---|
| 상태 | **Confirmed** (2026-09-23) |
| 최종 수정 | 2026-09-23 |
| 선행 문서 | PRD-03 (검색 대상 데이터), PRD-04 (검색 진입 UI) |
| 후행 문서 | PRD-06 (검색 결과 페이지 UI) |

## 1. 목적 / 배경

수집·번역된 뉴스와 논문을 사용자가 **키워드 / 제목 / 본문** 기준으로 찾을 수 있게 한다.
수집량이 하루 2회 배치로 누적되면 메인 그리드 스크롤만으로는 원하는 항목에 닿을 수 없다.

## 2. 범위

**포함:**
- 뉴스·논문 통합 검색 및 타입별 필터
- 제목 / 본문 / 키워드 검색
- 한국어(번역문)와 영어(원문) 동시 검색
- 검색 결과 페이지

**제외 (Non-goals):**
- 검색 결과 페이지의 **레이아웃·페이지네이션** → PRD-06
  (이 문서는 질의·색인·결과 데이터까지 책임진다)
- 개인화 추천, 검색 이력 기반 랭킹
- 자연어 질의응답(RAG) — 향후 별도 검토

## 4. "본문 검색"의 범위 — 확정 (2026-09-23, C-2 해소)

### 4.1 결정

후보 ③ **논문 전문만 색인**을 채택한다.
논문 PDF의 전체 텍스트를 **번역하지 않고 원문(영어) 그대로** 저장·색인한다
(PRD-03 FR-29). 뉴스 본문은 수집하지 않는다.

| 콘텐츠 | 저장·색인되는 텍스트 | 검색 불가 영역 |
|---|---|---|
| 뉴스 | 제목 + 요약문 (원문/번역) | **기사 본문 전체** |
| 논문 | 제목 + 3섹션(원문/번역) + **PDF 전문(영어)** | 없음 (PDF 확보 시) |
| 논문 (PDF 미확보) | 제목 + Abstract | 나머지 전부 |

**왜 ③인가** — 전문을 번역까지 하면 배치당 번역 콜이 PRD-03 §4.4의 320콜에서
수십 배로 뛴다. 색인만 하면 GPU 부하는 그대로이고 영어 질의가 논문 본문까지 도달한다.
뉴스 본문 스크래핑(②)은 매체별 파서 유지보수와 저작권 검토 부담이 커서 1차 범위 밖이다.

### 4.2 남는 비대칭 — UI에 반드시 명시할 것

**한국어 질의와 영어 질의의 도달 범위가 다르다.**

| 질의 언어 | 뉴스 | 논문 |
|---|---|---|
| 한국어 | 제목·요약 (번역문) | 제목·3섹션 (번역문) |
| 영어 | 제목·요약 (원문) | 제목·3섹션 + **전문** |

사용자가 "본문 검색"을 기대하고 한국어로 질의하면 논문 전문에 닿지 못한다.
이 격차를 숨기지 말고 UI에 드러낸다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-16 | 검색창 placeholder에 검색 범위를 적는다 (예: "제목·요약·논문 초록에서 검색") | Must |
| FR-17 | 결과 헤더에 적용된 검색 범위를 표기한다 | Should |
| FR-18 | 영어 질의로 논문 전문에서 매칭된 결과에는 "본문에서 발견" 표시를 붙인다 | Could |

## 5. "키워드 검색"의 해석 — 확정 (2026-09-23)

두 해석이 요구사항 상 구분되지 않았다. **둘 다 채택하되 용도를 나눈다.**

| 해석 | 의미 | 결정 |
|---|---|---|
| A. 태그 필터 | 수집 키워드(보안/해킹/사이버/AI)로 걸러보기 | **데이터는 Must, UI 노출은 PRD-06에서 결정** |
| B. 자유 키워드 | 임의 단어로 전체 텍스트 조회 | **채택** — FR-2·FR-3에 흡수된다 |

  기록하도록 Must로 두었다. 기록은 나중에 되살릴 수 없는 정보라 지금 쌓아야 하고,
  이를 필터 칩으로 노출할지는 PRD-06의 결정이다.

## 6. 기술 요건

### 6.1 검색 엔진 — 확정: PostgreSQL + `pg_bigm` (2026-09-23)

번역문이 한국어이므로 **한국어 검색 품질이 곧 서비스 품질**이다. 단순 `LIKE '%질의%'`는
조사 결합("랜섬웨어**가**"), 복합명사("공급망공격" ↔ "공급망 공격"), 어간("공격했다" ↔ "공격")을
처리하지 못한다. PostgreSQL 기본 FTS에는 한국어 형태소 분석기가 없다.

**결정: 별도 검색 서비스를 두지 않고 PostgreSQL 하나로 간다.**

| 대상 | 방식 | 근거 |
|---|---|---|
| 한국어 (`titleKo`, `summaryKo`, `sections[].textKo`) | `pg_bigm` 2그램 + GIN 인덱스 | 형태소 사전 없이 조사 결합·복합명사를 대부분 흡수한다 |
| 영어 (`titleOriginal`, `summaryOriginal`, `sections[].textOriginal`, `fullTextOriginal`) | PostgreSQL FTS `to_tsvector('english', …)` | 어간 추출 내장 |

**왜 이 선택인가** — 수집 상한이 일 260건(PRD-03 §4.4)으로 확정됐다. 이 규모에서
OpenSearch+Nori의 JVM 2~4GB 상주는 과잉이고, Meilisearch는 서비스가 하나 늘면서
DB↔색인 동기화 코드를 따로 써야 한다. `pg_bigm`은 `architecture.md` §2의
Docker Compose 구성에 **서비스를 하나도 추가하지 않는다.**

**한계와 대비책** — `pg_bigm`은 형태소 분석이 아니라 2그램이므로 관련도 랭킹(FR-8)이
형태소 기반보다 거칠고, 짧은 질의(1글자)에서 노이즈가 난다. `fullTextOriginal`까지
색인하면 인덱스 크기도 커진다. 운영 중 품질이 부족하면 **같은 DB 안에서 `mecab-ko`
확장을 추가**하는 경로를 남겨 둔다(서비스 추가 없이 확장만 교체).

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-19 | 한국어 색인은 `pg_bigm` GIN 인덱스로 구성한다 | Must |
| FR-20 | 영어 색인은 `to_tsvector('english', …)` 기반 GIN 인덱스로 구성한다 | Must |
| FR-21 | 1글자 질의는 거부하거나 경고한다 (2그램 특성상 노이즈가 심하다) | Should |
| FR-22 | 색인 컬럼은 생성 컬럼(generated column) 또는 트리거로 유지해 본문과 어긋나지 않게 한다 | Must |

## 10. 확정 사항 (2026-09-23) — 남은 미결 해소

### 10.1 `sections[]` 스키마 — JSONB 단일 테이블

**논문 섹션을 별도 테이블로 분리하지 않고, `contents` 테이블의 `sections` JSONB 컬럼에 둔다.**

| 이유 | 설명 |
|---|---|
| 생성 컬럼을 쓸 수 있다 | 같은 행 안에 있으므로 `searchKo`/`searchEn`을 `GENERATED ALWAYS AS (…) STORED`로 선언할 수 있다. 트리거 코드가 필요 없다 (FR-22) |
| 섹션은 최대 3개, 독립 조회가 없다 | 항상 논문과 함께 읽는다. 정규화 이득이 없다 |
| 스키마 변화에 강하다 | 나중에 Method를 추가해도 마이그레이션이 없다 |

```sql
sections JSONB   -- [{"name":"Abstract","textOriginal":"…","textKo":"…"}, …]

searchKo TEXT GENERATED ALWAYS AS (
  coalesce(title_ko,'') || ' ' || coalesce(summary_ko,'') || ' ' ||
  coalesce((SELECT string_agg(x->>'textKo',' ') FROM jsonb_array_elements(sections) x),'')
) STORED
```

> ⚠️ PostgreSQL 생성 컬럼은 **IMMUTABLE 식만** 허용한다. 위 서브쿼리는 그대로는 안 되므로,
> `IMMUTABLE` 마킹한 헬퍼 함수로 감싼다. 이것이 DB 구현의 첫 과제다(FR-23).

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-23 | `searchKo`/`searchEn`은 `IMMUTABLE` 헬퍼 함수를 쓴 생성 컬럼으로 만든다 | Must |

### 10.2 색인 크기 — 자르지 않는다

`fullTextOriginal`은 PRD-03 FR-52에서 이미 200,000자로 잘린다.
**색인은 그 전량을 대상으로 한다.** 일 60건 × 20만자 = 연 약 4GB 원문,
GIN 인덱스는 그보다 작다. 이 서버 디스크 1.8TB에서 문제되지 않는다.

### 10.3 관련도 랭킹

```
score = 3.0 × 제목 매칭
      + 1.5 × 요약/초록 매칭
      + 1.0 × 본문(fullText) 매칭
      + 0.3 × 최신성 보정 (최근 7일 이내면 가산)
```

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-24 | 관련도 정렬은 위 가중치를 적용하고, 가중치는 설정으로 조정 가능하게 한다 | Should |
| FR-25 | 기본 정렬은 **관련도순**(검색 결과), **최신순**(카테고리 목록) | Must |

### 10.4 자동완성 — 1차 미지원

`pg_bigm`만으로는 접두사 제안이 약하고, 별도 사전·인기어 집계가 필요하다.
검색어 로그(PRD-02 §7)가 30일 쌓인 뒤 인기어 기반으로 도입하는 편이 낫다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-26 | 1차 범위에서 자동완성을 제공하지 않는다 | — |
| FR-27 | FR-9(결과 없음 시 대체 제안)의 "인기 키워드"는 검색어 로그 집계로 채운다. 로그가 쌓이기 전에는 기본 4키워드를 보여준다 | Could |

### 10.5 검색어 로그

PRD-02 §7에서 확정 — **회원 ID와 연결하지 않고, 질의어·시각·결과 건수만 30일 보관.**

### 10.6 한국어 질의의 논문 전문 미도달 (§4.2) — 1차 수용

한국어로는 논문 전문에 닿지 못한다. 이를 **UI에 명시(FR-16·FR-17)하는 선에서 수용**하고,
전문 번역·요약 색인은 1차 범위 밖에 둔다. GPU 부하가 §4.1의 결정 근거 그대로이기 때문이다.

향후 경로 — `fullTextOriginal`을 요약 번역해 `fullTextSummaryKo`로 색인.
번역 콜이 논문당 1회만 늘어 부하 증가가 제한적이다. **2차 과제로 기록.**
