# PRD-03: 뉴스·논문 수집 및 AI 번역

| 항목 | 값 |
|---|---|
| 상태 | **Confirmed** (2026-09-23) |
| 최종 수정 | 2026-09-23 |
| 선행 문서 | — |

> 2026-09-23 전부 확정. 소스 목록은 §7, 번역 모델·운영 정책은 §8.
> **남은 것은 §9의 벤치마크 게이트(FR-42) 하나뿐이다.**

## 1. 목적 / 배경

'컴퓨터 및 정보 보안' 테마의 뉴스와 논문을 자동 수집하고, 외국어 콘텐츠를 AI로 번역하여
큐레이션한다.

## 2. 범위

**포함:**
- 기본 키워드 기반 뉴스·논문 자동 수집
- 수집 콘텐츠의 AI 번역
- 수집 결과 저장 및 메인 페이지 노출용 조회 API

**제외 (Non-goals):**
- 메인 페이지 렌더링 → PRD-04
- 논문 상세 페이지 UI → PRD-04 §10
- 검색 질의·색인 구현 → PRD-05
- 사용자별 맞춤 키워드 / 구독 → **PRD-01 §3에서 확정됨.** 구독은 수집이 아니라
  저장된 항목에 대한 필터이므로, 이 문서의 수집 파이프라인은 영향받지 않는다 (C-9 해소)

## 3. 수집 키워드 정책

### 3.1 기본 키워드 (Default Keywords)

서비스가 기본으로 수집하는 주제 키워드는 다음 4종이다.

| # | 한글 | 영문 대응 | 비고 |
|---|---|---|---|
| 1 | 보안 | security | 정보보안 전반 |
| 2 | 해킹 | hacking | 공격 기법, 침해 사고 |
| 3 | 사이버 | cyber | 사이버 위협·사이버전 등 |
| 4 | AI | AI | AI 보안, AI 기술 동향 |

- 국내 소스는 한글 키워드, 국제 뉴스·논문 소스는 영문 키워드로 질의한다
- 논문(arXiv 등)은 사실상 영문 질의만 유효하다

### 3.2 정책 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 위 4개 키워드를 기본 수집 대상으로 설정 | Must |
| FR-2 | 키워드를 코드 상수가 아닌 설정(DB 또는 설정 파일)으로 관리하여 재배포 없이 변경 가능 | Should |
| FR-3 | 여러 키워드에 동시 매칭된 항목의 중복 저장 방지(원문 URL 기준 dedup) | Must |

## 4. 수집 소스

### 4.1 확정 사항 (2026-09-23 질의응답)

| 구분 | 방식 | 결정 |
|---|---|---|
| 논문 | **arXiv + Semantic Scholar** | arXiv를 1차 소스, Semantic Scholar로 폭 확장 |
| 뉴스 | **RSS + 뉴스 API 병행** | 지정 매체는 RSS로 확보, 그 외 키워드 매칭은 API로 보완 |
| 수집 주기 | **하루 2회 (오전·오후)** | 뉴스·논문 동일 스케줄 |

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-21 | 논문은 arXiv API와 Semantic Scholar API 양쪽에서 수집한다 | Must |
| FR-22 | 뉴스는 등록된 RSS 피드와 뉴스 API 양쪽에서 수집한다 | Must |
| FR-23 | 수집 스케줄은 하루 2회(오전·오후) 배치로 실행한다 | Must |
| FR-24 | 소스가 달라도 동일 콘텐츠는 1건으로 합친다 — URL 정규화 후 dedup | Must |
| FR-25 | 특정 소스 장애 시 나머지 소스 수집은 계속 진행한다 (부분 실패 허용) | Must |
| FR-26 | 소스별 수집 성공/실패 건수를 배치 단위로 기록한다 | Should |

### 4.2 다중 소스 운영 시 유의점

**중복 제거(FR-24)의 실질적 부담** — 소스를 4종(arXiv, Semantic Scholar, RSS, 뉴스 API)
병행하면 같은 항목이 여러 경로로 들어온다. 단순 URL 문자열 비교로는 부족하다:

- 추적 파라미터 차이 (`?utm_source=...`) → 쿼리스트링 정규화 필요
- 리다이렉트/단축 URL → 최종 URL 해석 후 비교
- 동일 논문의 arXiv ID와 Semantic Scholar ID → **DOI 또는 arXiv ID를 우선 키로** 사용
- 같은 사건을 다룬 서로 다른 매체 기사는 중복이 아님 (제거 대상 아님)

**Semantic Scholar의 PDF 확보 한계** — 메타데이터는 풍부하나 PDF 전문(open access)이
없는 논문이 상당수다. 이 경우 5.4의 섹션 추출이 불가능하므로 **Abstract만으로 폴백**된다.
논문 카드에 "전문 분석 가능 / Abstract만" 상태를 구분해 표기할지 검토 필요(PRD-04 연계).

### 4.3 수집 주기와 번역 부하

하루 2회 배치는 **번역 부하가 2회에 집중**된다는 뜻이다. 배치 1회당
(수집 건수 × 제목) + (논문 건수 × 3섹션)만큼의 추론이 한꺼번에 발생한다.
GPU 8장 워커 풀이 이를 배치 간격 내에 소화해야 하며, 1회 수집량 상한을
정하지 않으면 다음 배치까지 밀릴 수 있다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-27 | 배치 1회당 수집 건수 상한을 **뉴스 100건 / 논문 30건**으로 두고, 설정으로 변경 가능하게 한다 (2026-09-23 확정) | Must |
| FR-28 | 번역 큐가 다음 배치 시작 시점까지 비워지지 않으면 경고를 남긴다 | Should |

### 4.4 수집 상한과 번역 부하 계산 (2026-09-23 확정)

| 항목 | 값 |
|---|---|
| 배치 1회 | 뉴스 100건 · 논문 30건 |
| 하루(2회) | 뉴스 200건 · 논문 60건 |
| 배치당 번역 콜 | 뉴스 100 × 2(제목·요약) + 논문 30 × 4(제목·3섹션) = **320콜** |
| GPU 8장 분담 | 장당 약 40콜 |

이 값이 R-1(GPU 부하 미검증) 리스크의 해소 근거다. 번역 모델이 선정되면
"장당 40콜 × 항목 길이"로 배치 소요 시간을 실측해 상한을 재조정한다.

## 5. AI 번역

### 5.1 목적

수집된 영문 콘텐츠를 AI로 한국어 번역하여, **영어에 익숙하지 않은 사용자도 내용을
파악할 수 있게** 한다. 특히 논문은 원문 전체를 읽지 않고도 핵심을 판단할 수 있어야 한다.

### 5.2 번역 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-4 | 영문 콘텐츠를 AI로 한국어 번역한다 | Must |
| FR-5 | 뉴스: **제목과 요약문**을 번역한다. 요약은 RSS/API가 제공하는 description 필드를 사용하며, 본문 전문은 번역·저장하지 않는다 (2026-09-23 확정) | Must |
| FR-6 | 논문: **Abstract / Introduction / Conclusion** 3개 섹션을 번역하여 제공한다 | Must |
| FR-7 | 논문 제목도 번역한다 | Must |
| FR-8 | 원문을 폐기하지 않고 함께 보관한다 (번역 오류 시 대조 가능해야 함) | Must |
| FR-9 | 번역 실패 시 원문을 노출하고, 번역 실패 상태를 기록한다 | Must |
| FR-10 | 국내 뉴스 등 이미 한국어인 콘텐츠는 번역 대상에서 제외한다 | Must |
| FR-11 | 보안 분야 전문 용어(예: ransomware, zero-day, supply chain attack)가 어색하게 번역되지 않도록 용어 처리 방안을 둔다 | Should |

### 5.2.1 표시 제목 폴백 규칙 (2026-09-23 확정 — C-6 해소)

FR-10(한국어 콘텐츠는 번역 제외)과 FR-9(번역 실패)로 인해 `titleKo`가 비는 경우가 있다.
화면에 무엇을 보여줄지 **스키마·API 수준에서** 다음 규칙으로 고정한다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-30 | API 응답에 표시용 필드 `titleDisplay`를 포함한다. 값은 `titleKo`가 비어 있지 않으면 `titleKo`, 아니면 `titleOriginal`이다 | Must |
| FR-31 | 요약문도 동일하게 `summaryDisplay = summaryKo ?? summaryOriginal` 규칙을 적용한다 | Must |
| FR-32 | 프론트엔드는 `titleKo`/`titleOriginal`을 직접 분기하지 않고 `titleDisplay`만 사용한다 | Must |

`translationStatus`가 `skipped`(국내 뉴스)든 `failed`(번역 실패)든 이 한 규칙으로 처리된다.

### 5.2.2 매칭 키워드 기록 (2026-09-23 확정 — PRD-05 §5 해석 A)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-33 | 수집 시 어떤 기본 키워드에 매칭되어 들어온 항목인지 `matchedKeywords[]`에 기록한다 | Must |
| FR-34 | 여러 키워드에 동시 매칭되면 전부 기록한다 (FR-3의 dedup과 별개) | Must |

기록 자체는 Must다(비용이 거의 없고 나중에 되살릴 수 없는 정보다).
이를 UI 필터로 노출할지는 PRD-06에서 결정한다.

### 5.3 논문 3개 섹션 선정 근거

| 섹션 | 역할 |
|---|---|
| Abstract | 연구 전체 요약 — 읽을지 말지 판단 |
| Introduction | 문제의식과 배경 — 왜 이 연구를 했는가 |
| Conclusion | 결과와 한계 — 그래서 무엇을 알아냈는가 |

이 3개로 "논문을 읽지 않고도 내용을 파악한다"는 목표를 충족한다. Method/Experiment는
분량이 크고 번역 품질 확보가 어려워 1차 범위에서 제외한다.

### 5.4 기술적 제약 — 섹션 추출

⚠️ **Abstract와 Introduction/Conclusion의 난이도가 다르다.**

| 대상 | 확보 방법 | 난이도 |
|---|---|---|
| Abstract | arXiv API 등 메타데이터에 구조화된 필드로 제공됨 | 쉬움 |
| Introduction / Conclusion | **PDF 본문을 내려받아 파싱해야 함** | 어려움 |

논문 PDF는 표준 구조가 없어 섹션 경계 검출이 필요하다. 고려 가능한 도구:
GROBID(학술 PDF 전용 구조화), PyMuPDF/pdfplumber(텍스트 추출 후 휴리스틱),
arXiv LaTeX 소스 파싱(`\section{}` 기준, 가장 정확하나 소스 미공개 논문 존재).

섹션명도 논문마다 다르다 — Conclusion이 "Conclusions", "Concluding Remarks",
"Discussion and Conclusion"으로 쓰이거나, Introduction 없이 바로 본론에 들어가는 경우도 있다.
**추출 실패 시 Abstract만으로 폴백하는 경로가 반드시 필요하다.**

### 5.4.1 논문 전문 저장 — 검색 색인 전용 (2026-09-23 확정 — C-2 해소)

PRD-05의 "본문 검색" 요구를 충족하기 위해, **논문 PDF의 전체 텍스트를
번역 없이 원문(영어) 그대로 저장하고 색인한다.**

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-29 | 논문 PDF에서 추출한 전체 텍스트를 `fullTextOriginal`에 저장하고 검색 색인 대상에 포함한다 | Must |
| FR-29a | `fullTextOriginal`은 **번역하지 않는다.** 번역 대상은 FR-6의 3개 섹션으로 유지한다 | Must |
| FR-29b | PDF를 확보하지 못한 논문(Semantic Scholar 경유 다수)은 `fullTextOriginal`이 비며, 이를 `fullTextStatus`로 구분 기록한다 | Must |
| FR-29c | `fullTextOriginal`은 화면에 노출하지 않는다 — 검색 색인 용도로만 쓴다 | Must |

**왜 번역하지 않는가** — 전문을 번역하면 배치당 번역 콜이 §4.4의 320콜에서
수십 배로 뛰어 GPU 8장으로 감당할 수 없다. 색인만 하면 번역 부하는 그대로이고
**영어 질의가 논문 본문까지 도달**하는 이득만 얻는다.

**남는 한계** — 한국어 질의는 여전히 제목·요약·3섹션 번역문 범위에서만 매칭된다.
뉴스 본문은 저장하지 않으므로(FR-5) 어떤 언어로도 검색되지 않는다.
이 범위를 검색 UI에 명시하는 것은 PRD-05 FR-3a의 몫이다.

### 5.6 온프레미스 번역 아키텍처 제약

서버 GPU: NVIDIA TITAN Xp × 8 (각 12GB, Pascal sm_61).

- **워커 풀 구성** — §8.1에서 **GPU 2장 × 4워커**로 확정됐다. 7B fp16이 12GB 1장에
  들어가지 않기 때문이다. 1장 × 8워커는 3B 대안으로 전환할 때의 구성이다
- **NUMA 그룹** — GPU 0~3 / 4~7이 서로 다른 NUMA 노드다. 워커의 GPU 짝은
  **그룹 경계를 넘지 않는다**(0+1 / 2+3 / 4+5 / 6+7). 워커끼리는 독립이라 통신이 없다
- **정밀도** — `bf16` 사용 금지(Pascal은 에뮬레이션, fp32의 절반 속도). fp32 기본, VRAM이 부족할 때만 fp16
- **FlashAttention 사용 불가** — sm_61 커널이 없다. SDPA는 math / mem-efficient 백엔드로 폴백시킬 것
- **모델 크기** — 12GB 제약상 7B급이 상한. fp16은 2장 필요 (양자화 경로는 Pascal에서 커널 지원이 불안정해 채택하지 않는다, §8.1)

**전량 번역의 부하** — §4.4에서 배치당 320콜(장당 약 40콜)로 산정됐다.
모델이 선정되면 실측으로 검증한다. `fullTextOriginal`(FR-29)은 번역 대상이 아니므로
이 계산에 포함되지 않는다.

### 5.7 섹션 추출 휴리스틱 설계

PDF 텍스트 추출 방식은 의존성이 가볍지만 **논문 형식 편차로 실패율이 높다.**
다음을 요구사항으로 둔다.

| ID | 요구사항 |

## 8. 번역 모델 및 운영 정책 확정 (2026-09-23)

### 8.1 모델 — 품질 우선 (2026-09-23 재정의)

> **이 서비스의 1순위는 수집 품질과 번역 품질이다. 속도는 제약 조건일 뿐 목표가 아니다.**
> 사용자가 2026-09-23에 명시했다: "가장 중요한 것은 수집과 번역 품질".
> 비상업·개인 사용이므로 NC 라이선스 모델을 쓸 수 있다.

#### 후보

| 모델 | 라이선스 | 한국어 | GPU |
|---|---|---|---|
| **EXAONE-3.5-7.8B-Instruct** | EXAONE 1.1 **NC** (비상업 한정) | KoMT-Bench **7.96** · LogicKor **9.08** | fp16 2장 |
| Qwen2.5-7B-Instruct | Apache 2.0 | KoMT-Bench 5.19 · LogicKor 6.38 | fp16 2장 (실측 완료) |

EXAONE은 **영어·한국어 이중 언어 전용 설계**이고 어휘 102,400으로 한국어 토큰 효율이
높다. LG 자사 발표 기준 한국어 지표가 Qwen 대비 40~53% 높다.
자사 수치이므로 **실데이터 A/B로 직접 검증한다**(§8.1.2).

#### 8.1.1 선정 절차

### 9.1 키워드와 카테고리의 관계 (정리)

키워드(보안/해킹/사이버/AI)와 카테고리(국제 뉴스/국내 뉴스/최신 논문)는 **다른 축**이다.

- **카테고리**는 출처와 형식으로 나뉜다 — 화면 구조(PRD-04 FR-13, PRD-06 FR-14)의 기준
- **키워드**는 주제로 나뉜다 — 수집 질의어이자 `matchedKeywords[]` 태그(FR-33)

카테고리 3종은 **고정**이다. 늘리려면 PRD-04·PRD-06의 화면 구조를 함께 고쳐야 한다.
키워드는 설정으로 자유롭게 늘릴 수 있다(FR-2).
